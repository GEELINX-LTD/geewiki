# 0010. 写入前置条件、主体授权与部署启动检查

- 状态：accepted
- 记录日期：2026-06-29
- 关联：ADR-0003、ADR-0006、ADR-0009

## 技术背景

编辑器保存前的 GET 与后续 PUT 之间仍有竞争窗口；GET 失败时跳过检查会覆盖别人提交的内容。
`wiki-service.save/remove` 面向受信系统插件，不携带用户主体，用户工具必须自行补授权。
管理器允许部分插件启动失败，因此进程仍存活不代表部署需要的核心服务可用。

## 考虑选项

1. 继续依赖客户端预读和各调用方分别授权。
2. 增加保存前置条件和主体写入入口，共用现有写入实现；部署组合根检查必要服务。
3. 立即拆分写服务、增加数据库迁移与完整插件沙箱。

## 决策结果

选择第二项，不新增依赖或数据库列。

- 原文读取向有编辑权的调用方返回 `revision`，由页面身份、标题、正文与更新时间计算。
  保存可传 `expectedRevision`：`null` 表示只允许创建，字符串表示只允许更新所读状态；
  不匹配返回 `409 edit_conflict`。不向无编辑权读者提供原文的派生令牌。
- PostgreSQL 在事务中锁定既有行，创建用唯一约束处理竞争；SQLite 的 Wiki 写事务在插件内排队。
  冲突发生在快照、块、出链和保存事件之前，不留下半次写入。
- 新增 `saveAs/removeAs`，显式接收主体并查询 `policy-service`；HTTP 与 AI 写工具使用它们。
  系统用 `save/remove` 保留，明确标记其不做用户授权。用户入口不接受创建可见性专属字段。
  这不是插件隔离：同进程受信插件仍可使用系统入口或访问数据库；授权检查也不宣称与并发 ACL 修改原子化。
- 标准部署启动必须拿到 HTTP、数据库、认证、策略、Wiki 服务，否则清理并抛错。
  显式自定义注册表继续支持最小宿主，并可指定自己的必要服务。
- CI 在现有 `build` 作业中运行生产环境核心流程验收，保持 required check 名称不变。

## 后果

### 正面

- 编辑器、AI 与 HTTP 共用服务端保存前置条件，过期内容不会直接覆盖当前内容。
- 用户写入的逐对象权限和归属在服务入口落实，减少遗漏调用方检查的机会。
- 标准部署失败会退出，核心流程回归进入已有发布门禁。

### 负面 / 风险（如实）

- 为兼容既有调用，未传前置条件的旧 HTTP 或服务调用仍保留无条件保存语义；
  第一方编辑器与 AI 写工具必须提交前置条件。
- SQLite 插件内排队不等于全应用的事务调度；其他插件共享连接的并发事务仍需单独治理。
- 必要服务检查只判断启动完成时的可用性；运行期健康探针与插件停用仍由现有机制负责。
- 核心验收增加 CI 时间，不能替代全部浏览器验收和 PostgreSQL 验证。
