# 0017. 插件界面浏览器验收进入构建门禁

- 状态：accepted
- 记录日期：2026-10-26
- 关联：ADR-0010、ADR-0014、ADR-0015、ADR-0016

## 技术背景

插件界面的入口失败、异步超时、作用域回收与实际注册诊断已经有隔离 CDP 验收，
但生产与 Vite 开发两条路径仍只在本地手动执行。单元测试与生产构建无法覆盖开发模式的动态导入改写，
也不能证明入口失败后真实界面、管理台提示及迟到注册的行为。

## 考虑选项

1. 保留手动运行，在 PR 描述中要求提供两种模式的结果。
2. 在现有 `build` 作业中执行两种模式，沿用 required check 与发布依赖链。
3. 新增独立浏览器作业或模式矩阵，并另行调整 GitHub 分支保护与发布依赖。

## 决策结果

选择第二项。构建成功后分别执行 `run-plugin-ui-diagnostics.mjs` 与同命令附加 `--dev`，
使用 runner 的 `google-chrome` 和既有隔离运行器；每种模式设置 5 分钟步骤上限。
只要产物构建成功且作业未取消，两步都执行，包括前一步或核心流程验收已经失败的情况。
任意一步失败仍使 `build` required check 失败，不使用 `continue-on-error`。

保留核心流程的独立 artifact；另在作业失败时上传插件界面两种模式的结果目录，保留 7 天。
目录中的结果 JSON、截图和服务/Vite/Chrome/CDP 进程日志共同用于排查；启动过早失败时可能没有截图。
脚本仍可用同样命令在本地复现。当前覆盖范围由 `docs/ci-cd.md` 解释，以 workflow 为最终事实。

## 后果

### 正面

- 生产产物与 Vite 开发路径的插件界面回归都会阻断现有构建检查和后续发布。
- 一个模式失败仍能取得另一模式的结果，缩短动态导入与生命周期故障的排查过程。
- 不增加浏览器依赖或构建模型，不需要新的 required check 名称与分支保护配置。

### 负面 / 风险（如实）

- 构建作业增加两轮浏览器启动与真实超时等待，执行时间和对 runner Chrome 可用性的依赖增加。
- 两模式串行运行共享一个作业的时间上限；runner 故障或作业取消时不保证两边都完成或 artifact 上传成功。
- 只验证 Chromium 下已登记的生命周期和诊断场景，不代表所有编辑器、触屏或其他浏览器均受门禁保护。
- 截图和进程日志仅限隔离测试夹具；人工拿生产实例替换运行器不属于这条 CI 契约。
